## 11. Testing and Validation of Honeypot Behavior

### Honeypot Protocol Compliance Verification

The verification of protocol compliance in a honeypot is a critical step in ensuring that the system accurately emulates the behavior of real industrial control systems (ICS) devices. In the context of Modbus and DNP3 protocols, this involves rigorous testing of both request and response mechanisms to ensure that the honeypot correctly interprets and generates messages according to the specifications defined by the respective standards. This section explores the methodologies used to validate protocol compliance, focusing on message structure, function code validation, register addressing, and error handling.

To begin, the verification process must ensure that the honeypot's message framing aligns with the expected format for both Modbus and DNP3 protocols. For Modbus, this includes checking the correctness of the transaction identifier (TXID), protocol identifier (PID), length field, and unit identifier in the Modbus TCP header. The transaction identifier is a 2-byte value that uniquely identifies each request, while the PID is typically set to 0x00 for Modbus TCP. The length field specifies the number of bytes in the payload, and the unit identifier identifies the target device. These fields must be validated against the Modbus TCP specification (IEC 60870-5-101:2002) to ensure that the honeypot generates messages that are structurally identical to those sent by real devices.

In addition to header validation, the function code within Modbus messages must be verified. For example, a Modbus read coil status request uses function code 0x01, while a write single register request uses function code 0x06. The honeypot must accurately interpret these function codes and generate corresponding responses that match the expected behavior of real devices. This includes validating the correctness of the data field in the message, which contains the actual register values or coil statuses being read or written. Any deviation from the expected structure can lead to misinterpretation by attackers, potentially reducing the honeypot's effectiveness as a target.

For DNP3, the protocol compliance verification involves checking the structure of the message headers and the use of application layer objects (ALOs). The DNP3 protocol defines specific message types, such as unconfirmed and confirmed messages, which are differentiated by the presence of a message sequence number (MSN) and a message acknowledgment (MSNACK). The honeypot must correctly generate these headers based on the type of message being transmitted. For example, an unconfirmed message does not include a MSN or MSNACK, while a confirmed message includes both. This distinction is crucial for ensuring that attackers interact with the honeypot in a manner consistent with real DNP3 devices.

Moreover, the verification process must include the validation of register addressing within both protocols. In Modbus, registers are addressed using a 16-bit address, and the honeypot must ensure that all read and write operations are performed on valid register addresses. This includes checking for out-of-range addresses, which can cause errors or unexpected behavior in real devices. Similarly, DNP3 uses a more complex addressing scheme that includes object classes, object instances, and attribute types. The honeypot must accurately map these attributes to the appropriate registers within the simulated device, ensuring that any read or write operation on a specific register corresponds to the correct object and attribute in the DNP3 specification (IEEE 1815-2003).

Another key aspect of protocol compliance verification is the validation of error handling mechanisms. In Modbus, errors such as invalid function codes, out-of-range addresses, or incorrect data lengths must be handled according to the standard error response format. For example, if a Modbus read coil status request is sent with an invalid address, the honeypot should respond with a Modbus exception code 0x02 (Illegal Data Value). This ensures that attackers are presented with responses that are consistent with real devices, thereby increasing the likelihood of interaction.

In DNP3, error handling is more nuanced due to the protocol's support for both unconfirmed and confirmed message types. For unconfirmed messages, errors may not be acknowledged, while confirmed messages include a retry mechanism. The honeypot must correctly implement these behaviors based on the type of message being transmitted. This includes ensuring that the message sequence number (MSN) is incremented appropriately for confirmed messages and that the acknowledgment (MSNACK) is generated in response to successful transmissions. Any deviation from this behavior can lead to inconsistencies in the honeypot's interaction with attackers.

To validate these aspects, the honeypot can be tested using a combination of automated testing frameworks and manual inspection. Automated tools such as Wireshark or tcpdump can capture and analyze the actual messages sent between the honeypot and attackers, allowing for detailed comparison against expected protocol behavior. For example, Wireshark's Modbus and DNP3 dissectors can be used to verify that the message headers, function codes, and register addresses are correctly formatted according to the respective standards.

In addition to automated testing, manual inspection of the honeypot's codebase is essential for identifying any potential discrepancies in protocol implementation. This includes reviewing the logic that handles message parsing, function code execution, and error generation. For example, the code responsible for handling a Modbus read coil status request must correctly extract the starting address and quantity of coils from the message payload, validate these values against the device's register map, and generate the appropriate response. Similarly, the code for DNP3 must correctly interpret the object class and attribute type from the message header and map them to the corresponding register within the simulated device.

Another important aspect of protocol compliance verification is the validation of the data types used in both protocols. Modbus uses 8-bit, 16-bit, and 32-bit data types for register values, while DNP3 includes additional data types such as bit strings and floating-point numbers. The honeypot must ensure that all data fields are correctly interpreted and formatted according to these specifications. For example, a Modbus write single register request must be validated to ensure that the data field is a 16-bit value, while a DNP3 write single register request may require additional validation of the data type based on the attribute being written.

Furthermore, the verification process should include testing for compatibility with different versions of the protocols. For example, Modbus TCP has evolved over time, and newer versions may introduce changes in message formatting or function codes. The honeypot must be tested against these versions to ensure that it can correctly emulate devices that support both legacy and modern implementations. Similarly, DNP3 has multiple versions, such as DNP3 v1.1 and v2.0, which include different message structures and object classes. The honeypot must be configured to support the specific version of DNP3 that it is intended to emulate, ensuring that attackers interact with it in a manner consistent with real devices.

In summary, the verification of protocol compliance in a honeypot involves a comprehensive set of checks that ensure the correct formatting, interpretation, and generation of messages according to the specifications of Modbus and DNP3 protocols. This includes validating message headers, function codes, register addressing, error handling, and data types, as well as testing for compatibility with different protocol versions. By rigorously testing these aspects, the honeypot can accurately emulate real ICS devices, making it an effective target for attackers and providing valuable insights into their behavior.

These signatures are often derived from known attack vectors documented in sources such as the ICS-CERT advisory reports, the MITRE ATT&CK framework, and vulnerability databases like CVE. By matching incoming traffic against these signatures, modpot can quickly identify potential attacks without requiring extensive computational resources.

Once a signature is matched, the honeypot employs rule-based detection to refine its classification of the event. This phase involves applying a set of predefined rules that further analyze the context of the detected pattern. For instance, if a Modbus Read Multiple Registers function code is identified, the system may check whether the request includes an unusual number of registers, such as exceeding the typical range used in normal operations. Similarly, for DNP3, the honeypot might evaluate the type of object being accessed and the frequency of access attempts to determine if they align with known reconnaissance or exploitation tactics. These rules are often based on empirical data collected from real-world attacks and are continuously updated to reflect new threats. By incorporating these validation steps, modpot ensures that its logs accurately reflect the behavior of real-world attackers while minimizing noise from benign activity.

### False Positive/False Negative Rate Analysis in Log Capture

The False Positive/False Negative Rate Analysis in Log Capture is a critical component of validating the effectiveness and reliability of a honeypot system. This analysis focuses on the accuracy of log capture mechanisms in recording attacker interactions with the Modbus/DNP3 ICS honeypot, particularly in distinguishing between legitimate and malicious activities. The log capture process must be both precise and robust to ensure that the data collected is representative of actual attacker behavior while minimizing errors that could skew the results of subsequent analysis. False positives occur when the system erroneously logs an interaction as malicious, whereas false negatives occur when a malicious interaction is not logged or misclassified. Both types of errors can significantly impact the quality of the honeypot's data and the conclusions drawn from it.

To evaluate the false positive and false negative rates, it is essential to define clear criteria for what constitutes a "true positive" (a genuine attacker interaction) and a "true negative" (a benign interaction). In the context of a Modbus/DNP3 honeypot, true positives would include actions such as register reads or writes that are intentionally malicious, such as attempting to exploit known vulnerabilities or probing for system weaknesses. True negatives would include benign interactions, such as routine maintenance operations or network traffic that does not engage with the honeypot's registers. The false positive rate is calculated as the ratio of false positives (erroneous logs) to the total number of logs, while the false negative rate is the ratio of false negatives (missed malicious logs) to the total number of actual malicious interactions.

The accuracy of log capture mechanisms depends on several factors, including the configuration of the honeypot's register monitoring system, the timing and frequency of log entries, and the presence of noise or interference in the network. For instance, if the honeypot is configured to log every register read or write without filtering, it may generate a high volume of false positives. Conversely, if the logging mechanism is too restrictive, it could miss some malicious interactions, leading to false negatives. Therefore, the design and implementation of the log capture system must balance sensitivity and specificity to minimize errors while maintaining sufficient data for analysis.

The false positive rate can be influenced by various mechanisms within the honeypot's architecture. One key factor is the use of register monitoring triggers. For example, if the honeypot is set to log every time a register is accessed, it may capture both benign and malicious interactions, increasing the likelihood of false positives. However, if the honeypot employs more sophisticated triggering mechanisms, such as detecting anomalies in register access patterns or using machine learning to classify interactions, it can reduce false positives by distinguishing between normal and malicious behavior. For instance, a honeypot that uses threshold-based detection for register writes—such as logging only those writes exceeding a certain frequency or magnitude—can filter out benign traffic while capturing potential attacks.

Another mechanism that affects the false positive rate is the use of packet filtering and classification rules. The honeypot must accurately identify and isolate Modbus/DNP3 traffic from other network protocols to ensure that only relevant interactions are logged. If the filtering rules are too broad, they may include non-Modbus/DNP3 traffic, leading to false positives. Conversely, if the rules are too narrow, they may exclude legitimate Modbus/DNP3 interactions, increasing the risk of false negatives. For example, a honeypot that uses deep packet inspection (DPI) to analyze the payload of each packet can more accurately identify Modbus/DNP3 frames and reduce the likelihood of logging non-relevant traffic.

The false negative rate is closely tied to the honeypot's ability to detect and log malicious interactions. If the honeypot fails to capture certain types of register accesses due to configuration errors, timing issues, or insufficient monitoring coverage, it may result in false negatives. For instance, if the honeypot is configured to monitor only a subset of registers, it may miss attacks that target other registers. Similarly, if the logging mechanism has a delay in capturing register writes, it may fail to log some malicious interactions in real-time, leading to missed events.

To mitigate false negatives, the honeypot's logging system must be designed with sufficient coverage and responsiveness.
